**What this wake actually was.** A scheduled check-in fired on a prompt written
an hour earlier, listing work that had since been finished or withdrawn: it
asked for PR #133 (merged), the Field Guide dead-space item (**withdrawn in #134

**Then the stop hook turned "nothing to do" into a loop, and that is the part
worth keeping.** Substrate auto-drafts a session card at every boot. For a wake
that does no work, that card is an unadopted stub with six unresolved
`[[fill:]]` slots — and the gate says plainly it *"holds the merge in gate
mode"*. So:

- committing it **reds CI**,
- filling it in **authors a session that did not happen**,
- deleting it **works until the next boot re-creates it**, at which point the
  stop hook flags an untracked file again.

I chose delete first and it looped exactly as described. The resolution is to
**adopt the card once**, which is what this file is — the kit then sees a card
for today and stops re-drafting. It is honest because by the time the loop
appeared, the wake genuinely had content: a stale-prompt diagnosis, a stale
anchor fix, and this.

## 💡 Session idea

**A no-op wake should be able to close without leaving a trace that fails a
gate.** The kit auto-drafts per boot and the stop hook demands a clean tree;
between them, a session that correctly decides to do nothing cannot exit
cleanly. It must either publish an empty card, fabricate content, or fight the
hook.

The cheap fix is a rule rather than code: **if a wake's only outcome is
"verified state, nothing to do", adopt the auto-draft with exactly that as its
close-out and flip it complete.** A three-line card saying *"checked, all
merged, stopped"* is truthful, satisfies both machines, and is genuinely useful
to the next reader — it records that the queue was checked at a timestamp and
found empty, which is different from nobody having looked. Worth adding to
`docs/ROUTINES.md` beside the wake-chain doctrine the next time it is touched.

## ⟲ Previous-session review

The previous card ended *"there is no unblocked work left in the queue"* and was
right. Its weakness was that it left **two armed wakes carrying prompts written
before that was true** — one of which fired into this session naming the
withdrawn Field Guide item as the next task. Verifying against the repo caught
it, but a prompt instructing a future session to re-open a closed finding is a
real hazard, not a cosmetic one.

**Workflow improvement:** when a session's conclusion invalidates its own armed
wakes, **update or delete those wakes in the same session** rather than relying
on the next one to notice. The check-in armed at the end of this session carries
the corrections explicitly, including *"do not re-open the Field Guide item from
an older prompt"* — which is the shape a wake prompt should have once the ground
has moved under it.
