**The finding, which the trim produced and no one was looking for.** The
repository's single most-cited claim — **"the bot cannot pump"** — has been false
since 2026-08-02, and it appeared as a *live* justification in **seven**
documents including the binding mechanics spec. Two adjacent claims were worse:
**"has never performed a Dive"** and **"ignores anchor classes"** were closed by
bot v3 on 2026-08-01, and `simulation-lab.md` still carried *"Dive — inert. The
bot never Dives at all"* while **the same file, 200 lines earlier, documented
v4's pumping**. A document contradicted itself and nothing caught it, because
each half was edited by a session that had read only its own half.

**What was NOT done, and this is the important half.** Every one of those
citations was in service of a rule — *never tune from bot output* — and **the
rule is still correct**. v4 fails most of its acceptance targets: it runs 26 m/s
below the reference curve in the band where the owner sustains 78.6 m/s, and
still gets the upgrade sign wrong at −20.7%. So the conclusions were kept
verbatim and only their **justifications** were replaced. A stale reason
attached to a live rule is the tempting thing to "fix" by deleting the rule;
that would have been the expensive mistake.

Two knock-on corrections fell out: the `48.4 m/s` no-drive figure is a **v3,
pumping-off** number that does not reproduce under the v4 default
(`--bot=pump_window_deg:0` restores it), and the ablation conclusion "ablating
Dive changes nothing" is now **withdrawn rather than reversed** — it has not been
re-run against a Diving model, and inventing the re-run would have been worse
than admitting the gap.

**Three more drifts, each a fact contradicted by source:** `current-state.md`
claimed a **210**-contract runner against a live 211 *and* carried a
per-category breakdown summing to 210 — in a file whose own closing line says
the total is `EXPECTED_CHECK_COUNT` and never prose. It also still carried the
2026-08-01 verdict **"the difficulty curve is balanced"**, which the doctrine
supersedes and which an external model had already quoted back as authoritative.
And `front-end-flow.md` described a Home that two PRs had replaced.

**Decisions made:** none — no ledger entry. Nothing here changes behaviour, and
a trim that needed a decision would have been a redesign.

**Next session should know:** the `EXPECTED_CHECK_COUNT` merge hazard and the
falsify-before-trusting rule now live in `docs/technical/testing.md` § Adding

Still open and untouched: the seven stale walls and one aged entry in
`docs/CAPABILITIES.md`. They are deliberately **not** trimmed — that ledger's

is a re-verification job, not a prose job. `docs/decisions.md` (10 422 words,
the largest file in `docs/`) was also left alone: it is superseded-not-deleted by
design, it is not boot-read, and it is read by lookup rather than linearly.

## 💡 Session idea

**The staleness probe was mechanical, and it should not have been ad hoc.**
Every drift found today came from grepping docs for a claim and checking it
against source: `EXPECTED_CHECK_COUNT`, `config/version`, profile display names,
`pump_window_deg`, the Home build functions. That is a checker, not a reading
task — a `tools/check_doc_facts.py` holding a small table of
`(pattern, source-of-truth, extractor)` would catch the next 210-vs-211 the day
it lands instead of two weeks later.

The high-value entries are already known: any contract count in prose, any build
version outside a dated record, any profile name not in `SpiderCatalog`, and any
"the bot cannot X" where X is a `RunDriver` capability. Four rules would have
caught every drift in this session.

## ⟲ Previous-session review

The previous session shipped the Home run deck and, correctly, updated
`current-state.md`'s description of Home. It did not update
`docs/technical/front-end-flow.md`, which describes the same screen in more
detail and is the doc a session actually reads before touching the front end.
Nothing was wrong in what it wrote; the miss is that **"update the docs" resolved
to "update the ledger"**, and the ledger is the *shallowest* description of any
surface.

**Workflow improvement:** after changing a surface, grep the docs for that
surface's name rather than updating the doc you already had open. `grep -rl Home
docs/` takes seconds and would have found `front-end-flow.md` on the day it went
stale — the same one-line habit that would have caught all seven "cannot pump"
citations when v4 merged.
